# Native online update, automatic rollback and configuration package (F-3a)

> atom: removed in step 1 (atom design 7.1). The atom installer installs and upgrades the programs, the configuration and the WebUI. Kept as history.

Status: implemented in `rust/native-host/src/update/`. Validation: [10-18-f3a](../validation-records/10-18-f3a/README.md).
Design notes and the Go comparison: the task's `research/design.md` / `go-semantics.md`.

## Scope and decisions (user, 2026-10-18; source and names changed 2026-10-22)
- Releases come from **`jasonxtt/atomdns`** (since the rename to AtomDNS, 2026-10-30; before that the repository was `jasonxtt/rtdns` with asset names `rtdns-*`, and earlier the Rust program used `rust-vX.Y.Z` tags in `jasonxtt/mosdns`, which were never published and are no longer recognised). Tags are **`vX.Y.Z`**, written exactly so (`v0.2.0`); only those are considered (not draft, not prerelease). `rust-v…`, `lite-v…`, `openwrt-v…`, `V1.0.0`, `v1.0`, `v1.0.0-rc1` and the like are ignored. There is no bridge release: a program older than `v0.2.0` (the manually deployed `rust-v0.1.4`) still looks at the old repository and finds nothing, so it is replaced by hand once ([release.md](../release.md)). Linux amd64 only (`architecture: "linux/amd64"`; other platforms report the capability as unsupported).
- An upgrade is the program plus, when the release needs a newer one, the `config_rust` package, plus (since v0.4.0, user decision 2026-10-24) the WebUI `<root>/ui/main/` **when that directory exists**: the program embeds no UI any more ([native-webui-hosting](native-webui-hosting.md)). A host without `ui/main` stays a pure backend (nothing is downloaded or created); other `ui/<name>` directories are never part of an upgrade. Updating *to* v0.4.0 from v0.3.0 (whose updater does not know the WebUI asset) needs the one manual step in [release.md](../release.md); no automatic transition exists.
- A failed upgrade is rolled back automatically; this must not depend on `systemd` (the production unit is `Restart=always`, `RestartSec=2min`).
- The first switch from Go to Rust is a deployment script (F-3b), not this feature.

## Container mode (Docker image, 2026-11)
`ATOMDNS_CONTAINER=1` (set by the image) turns the online updater off for **every** platform and architecture: `system.update` is unsupported with the reason "容器版请拉取新镜像并重建容器…", `POST /api/v1/update/apply` answers `501`, `update/status`/`check` report `update_available: false` with that message (the WebUI hides the whole update block through the capability). `config/export` stays. Instead, `main` runs `update/container.rs::prepare` before anything is loaded: an empty configuration volume is filled from the image's `config_rust.zip` (a non-empty directory without the configuration file is refused); an applied schema below `REQUIRED_CONFIG_SCHEMA` gets the image's `config_rust_up.zip` applied like the guard does (backup under `backup/container-schema-…`, state file written); an existing `ui/main` directory whose `ui_version` differs from the image's `atomdns-webui.tar.gz` is replaced by two renames through `update/`. The files are in `ATOMDNS_CONTAINER_ASSETS` (default `/usr/share/atomdns`). See [docker.md](../docker.md).

## Versions
`atomdns version` and `GET /api/v1/system/health` `version` print the build version: the release tag (`ATOMDNS_BUILD_VERSION=vX.Y.Z`), or `v<crate version>` for any other build. The candidate of an update must report exactly the release tag. An update is *available* only when the release is strictly newer (Go also counts downgrades); `force` reinstalls.

## HTTP API (WebUI `/`)
| Route | Behaviour |
| --- | --- |
| `GET /api/v1/update/status` | Within 3 s, from a 15-minute cache. A failed check is still `200` with `message: "检查更新失败：…"`. |
| `POST /api/v1/update/check` | Forces a check (8 s). Same degraded answer on failure. |
| `POST /api/v1/update/apply` | Optional body `{"force": bool, "prefer_v3": bool}` (`prefer_v3`: switch a baseline install to the `atomdns-linux-amd64-v3.tar.gz` build, same version allowed; `502` when the CPU lacks x86-64-v3 or the release has no v3 package or its manifest lacks the v3 sha256; ignored when the running build is already v3. A running v3 build always updates to the v3 package, a baseline build never moves to v3 on its own. On a musl system — a musl build, or `/etc/alpine-release` exists — the program asset is always `atomdns-linux-amd64-musl.tar.gz`: `prefer_v3` is refused there, `amd64_v3_capable` is not reported, and a release without the musl package is refused instead of falling back to the glibc one). Bad body `400 {"error"}`; nothing newer and not forced `200 {status, installed:false, restart_required:false}`; any refusal `502 {"error"}` (`409` while another update or restart is running, `501` where updating is unsupported); success `200 {status, installed:false, restart_required:true, notes}` with `status.pending_restart: true`. |
| `POST /api/v1/config/export` | Body `{"dir"}` → `application/zip`, `Content-Disposition: attachment; filename="atomdns_backup_<unix>.zip"`. Missing `dir` → `400 dir is required`; undecodable body → `400 Invalid request body` (plain text). |
Other methods are `405`. **Removed (UI redo part 1, 2026-10-23):** `POST /api/v1/config/update_from_url` (apply a configuration package from a URL) no longer exists and answers `404`; configuration packages arrive only with a program update (`update/apply`). `UpdateStatus` has Go's fields (`current_version`, `latest_version`, `release_url`, `architecture`, `asset_name`, `download_url`, `asset_signature`, `current_signature`, `published_at`, `checked_at`, `cache_expires_at`, `update_available`, `cached`, `config_schema_required`, `config_schema_applied`, `config_update_status/_message/_error/_backup`, `config_package_id`, `message`, `pending_restart`, `rollback_performed`, `rollback_message`; empty optional fields are omitted). `amd64_v3_capable` (CPU runs x86-64-v3) and `current_is_v3` (running build is v3) are present only when true. Not applicable here: `config_auto_updated` (always 0: the guard applies the package).
Differences from Go, all on purpose: **only this host's own configuration directory** is exported (`dir` must be the real configuration root; Go reads any directory the client names); a configuration package is accepted only when valid (manifest, sha256 per file, managed paths), never an arbitrary zip; the export leaves out `backup/` and `update/` and does not follow symbolic links, with a 128 MiB limit and **one export at a time** (a second one gets `503 another export is in progress` until the first response has been written), because each is built in memory; downloads are size- and time-bounded.
Capabilities `system.update` / `system.config_management` are *supported* when the platform is linux/amd64 (update only), the host has a configuration root, and the process captured its executable path; otherwise they report why. `GET /api/v1/system/health` shows `required_config_schema`, `applied_config_schema`, `config_management_enabled` and `update: {state: idle|pending|rolled_back, …}` (never affects `ready`).

## Release layout
- `atomdns-linux-amd64.tar.gz` (one file named `atomdns`; the updater installs it over the running program's own path, whatever that file is called), `atomdns-webui.tar.gz` (v0.4.0: the WebUI package, its files at the top level; `ui-manifest.json` `ui_version` = the tag), `atomdns-update-manifest.json` (`format 1`, `channel "rust"`, `version`, `required_config_schema`, `config_package_id`, `artifacts{name:{sha256}}`, optional `config{url,sha256}`; unknown fields are refused). The WebUI is one more key of `artifacts`, not a new field: older updaters refuse unknown top-level fields but take any artifact name, so a v0.3.0 host can still read a v0.4.0 manifest. The release listing is read from `https://api.github.com/repos/jasonxtt/atomdns/releases?per_page=100` (`ATOMDNS_UPDATE_API_URL` replaces it for tests or mirrors; nothing skips the sha256 checks). Downloads use the configured `socks5_proxy` object (then directly if the proxy fails).
- `scripts/build-rust-release.sh vX.Y.Z` builds the artifacts (the WebUI with `UI_VERSION=<tag> npm run build:package`; `PREBUILT_WEBUI` takes a ready one) and `scripts/generate-rust-update-manifest.sh` the manifest (it requires both `atomdns-linux-amd64.tar.gz` and `atomdns-webui.tar.gz`, and refuses when `scripts/rust-release-metadata.json` and the constants in `update/mod.rs` disagree, including the three asset names). Nothing is published by these scripts; see [release.md](../release.md) for the steps.
- Configuration package `config_rust_up.zip` (built by `file/atomdns/config/incremental/build_config_rust_up.sh`; since v0.5.0 the package lives in the file repository and `config.url` is a commit-pinned `raw.githubusercontent.com/jasonxtt/file/<commit>/atomdns/config/incremental/config_rust_up.zip` — the updater accepts any URL and checks only the manifest's sha256; up to v0.4.2 it was an asset of the same release; order in [release.md](../release.md)): `manifest.json` + the managed files, `channel "rust"`, `config_schema`, `package_id`. Managed: `config_custom.yaml` and `sub_config/*.yaml` except the host-generated `special_groups.yaml`; `create_if_missing` only `rule/switchN.txt` (`A`/`B`; empty since schema 3); `delete_files` only `sub_config/*.yaml`. The program requires `REQUIRED_CONFIG_SCHEMA = 7` / `REQUIRED_CONFIG_PACKAGE_ID = "rust-config-schema-7"` (schema 7, 2026-11-05: the default configuration opens only `:53` and the API; `rewrite` uses `dns: $sequence_local_in` and `requery` uses `resolver: $sequence_requery`, both run inside the process, so the 2222 and 3066 listeners, the 7777/8888/3333/4444/3077/3099/3111 ones, `for_singbox.yaml` (in `delete_files`), `cache_node` and the unreferenced fake-IP sequences are gone; the eight `sequence_ipv4/ipv6_cnfakeon/off[_requery]` sequences became `process_listed.yaml` (`sequence_listed[_requery]`, marks in priority order) plus `sequence_unlisted_v4[_requery]` / `sequence_unlisted_v6` with `cn_fakeip` decided by `flag` matchers (verified identical in compat mode by `tools/config-diff`); safe mode now asks only foreign DNS for names outside every list: no domestic retry, remembered-direct names resolve through foreign (`sequence_foreign_exit_requery` for requery), a failed foreign AAAA lookup is returned as the error instead of being proxied, and DDNS with `ddns_foreign` has no domestic fallback; explicit lists, DDNS default, designated clients, rewrite targets and special groups still use domestic DNS; a program older than schema 7 cannot load this configuration; schema 6, 2026-10-30: `cache.yaml` defaults lowered — `lazy_cache_ttl` 604800, `size` 100000/50000/20000, `dump_interval` 21600 — and optional `label`s on caches and `route_learn` rules, see [native-settings.md](native-settings.md); every cache is rebuilt empty once; schema 5, 2026-10-29: the `output_tag`s of the four subscription sets are renamed 直连域名/代理域名/中国域名/非中国域名, matching the WebUI; matching logic and order unchanged, see [native-audit-control.md](native-audit-control.md); schema 4, 2026-10-24: `aliapi` `show_when`, `ddns_foreign` moved to the `mode` section, requery branches by `dns_mode`; no data migration; schema 2, 2026-10-23: learned routes moved from `domain_output` to `route_learner`, see [native-route-learner.md](native-route-learner.md); schema 3, 2026-10-23: `switch1`–`switch17` became `feature_flag`s in `sub_config/flags.yaml` and `sub_config/switch.yaml` is in `delete_files`, see [native-feature-flags.md](native-feature-flags.md); an older package is refused, and a `switchN` plugin or matcher fails to load); binary-only releases leave them unchanged and a structural change of the managed files bumps both. The package state is **`webinfo/rust_config_update_state.json`** — never the Go host's `config_update_state.json`.

## Safety rules (all enforced, all tested)
1. The program asset's sha256 must equal the manifest's; the package's sha256 must equal the manifest's and every managed file must match the package manifest; the candidate must report exactly the release tag (`candidate version`); a mismatch anywhere stops before anything is changed.
2. Before the service is touched, the candidate is run against the *new* configuration (`candidate check` on a scratch root built from links and the package's files): a program or package the new program rejects fails the request with the reason, and DNS never notices.
3. Only managed files are written (never the host-generated `sub_config/special_groups.yaml`, neither as a managed file nor in `delete_files`); every target is refused if it is reached through a symbolic link; each file is replaced atomically and durably (temporary file, fsync, rename, directory fsync) and each deletion is made durable by a directory fsync as well.
4. The old program, the old managed files and the old package state are saved in `<root>/update/txn-*/` **before** anything changes, and the directory entries leading to the transaction (`update/`, the configuration root) are flushed before the guard starts. A program update is refused up front when the program's own directory cannot take a new file (installing and rolling back both need it).
5. The WebUI (only when `<root>/ui/main` is a real directory; a symbolic link or a file there is left alone and the answer's `notes` says so): the manifest must list `atomdns-webui.tar.gz` and the release must carry it, or the **whole update is refused** (`502`); its sha256 must equal the manifest's (32 MiB download limit); before staging completes it is unpacked into a scratch directory and must be a WebUI package — plain files and directories only (no links, devices, FIFOs or pax headers; no absolute, `..`, hidden, backslash or control-character paths; at most 4096 entries, depth 8, 16 MiB per file, 64 MiB in all), a regular `index.html` and a `ui-manifest.json` with `manifest_schema` 1 and a `ui_version` (the interface level is judged by the candidate's own registry, see the health condition below); `update/` and `ui/` must be on the same filesystem (the swap is a rename). The transaction's WebUI paths must be exactly its own `txn-*/atomdns-webui.tar.gz`, `txn-*/webui/new` and `txn-*/webui/previous` (anything else is refused before anything is touched); `ui/` must still be a real directory (not a symbolic link) whenever `ui/main` is moved, at install and at rollback; the unpacked tree is flushed (every file and directory) before it is renamed into place.

## Transaction and rollback
States: `staged` → `installing` → `testing` → `verified`, or `rolled_back` (file `update/txn-*/transaction.json`; v0.4.0 adds `webui_archive_path`, `webui_sha256`, `webui_new_dir`, `webui_previous_dir`, all optional and inside `update/`, so older transaction files still read). After a verified update the old WebUI stays in `webui/previous` until the transaction directory is cleaned up at the next start, like the old program copy.
1. **Stage** (in the running host): downloads and checks as above, writes the transaction directory (old program copy, candidate, package, backups) and, last, `transaction.json` (`staged`). Live files are unchanged. A failure removes the directory.
2. **Hand-over** (750 ms after the answer): the host drains and saves exactly as for `SIGTERM`/restart, then `exec`s the *old* program's copy as `atomdns update-guard --transaction <file>` — **the same process id**, so a service manager never sees the service stop.
3. **Guard** (old code, no sockets): `installing` → writes the package files and state → (WebUI) re-checks the staged `atomdns-webui.tar.gz` sha256, unpacks it into `txn-*/webui/new`, renames `ui/main` → `txn-*/webui/previous` and `webui/new` → `ui/main` (each rename followed by an fsync of both directories) → installs the candidate over the program (atomic rename) → `testing` → starts the candidate as its **child** (`ATOMDNS_UPDATE_GUARD_TXN` set; the child asks to die with the guard, and exits at once if the guard has already gone) → polls the candidate's health (default 60 s; 3 consecutive `200 && ready && version == tag && applied_config_schema ≥ required`, and, when the WebUI was replaced, `external_ui` showing `main` mounted — a new WebUI the new program refuses rolls everything back). Healthy → writes `verified` first, then stops the candidate, records `update/installed.json` and `exec`s the final program (same arguments, same process id). Not healthy, exited, or timed out → stops it and **rolls back**. While on trial the candidate does not write its one-time feature-flag migration into `webinfo/settings.json` (a file the guard does not restore) and refuses flag changes; the final program writes it ([native-feature-flags](native-feature-flags.md)).
4. **Rollback** (idempotent): restores the configuration files and package state from the backup (existing files rewritten, files that did not exist removed), puts the old `ui/main` back when `webui/previous` exists (a `ui/main` in its place is moved to `webui/failed-N` first; without `webui/previous` the old directory was never moved and nothing changes; a failure to look at either directory is an error, never "absent", so the state stays for the next start), checks the saved program's sha256 and installs it, **then** writes `rolled_back` with the reason, then `exec`s the old program again (the program file is rewritten only when it is not already the old one). A config-only update (`kind "config"`) has no program swap and is otherwise identical; since `update_from_url` was removed no route starts one, and the guard keeps handling the kind only for transactions recorded by an older program.
5. **Recovery at every start** (before the configuration is loaded): any `installing`/`testing` transaction not belonging to the guard's own candidate is rolled back the same way and the old program is started; stale `staged` ones are closed; confirmed ones are cleaned up. A rollback that cannot complete leaves the state as it was and fails the start rather than running a mixed state.

Why this does not depend on `systemd`: the guard *is* the service's main process, the candidate is its child, and every ordinary failure (candidate crash, no start, unhealthy, timeout, pre-flight, write error) is handled by the guard within seconds without the main process ever exiting, so `RestartSec` never applies. Only if the guard itself is killed (`kill -9`, OOM) does the main process disappear; the candidate dies with it, the service manager starts the installed program after `RestartSec`, and the recovery above rolls back before the host runs. Power loss is the same: states are durable, so `installing`/`testing` are recognised after boot.

Interruption table: before `installing` nothing live has changed; during `installing` any prefix of the file writes is undone from the backup; between the two WebUI renames `ui/main` is missing and `webui/previous` holds it, which the rollback puts back; the program swap is one rename; from `testing` on, the candidate is on trial and any interruption rolls back; `verified` is written only after the candidate proved healthy, so a kill after it leaves a consistent new installation.

## First Go → Rust installation (F-3b)

`scripts/cutover/go-to-rust.sh` and `rust-to-go.sh` are Linux amd64 root/systemd
operator tools, separate from the running host's updater. They use the native
`config_rust_up.zip` manifest and Go schema-4 `config_up.zip` + `config_all.zip`
reference bytes. Managed differences require per-path explicit acceptance of
the native package version; all unmanaged data is copied unchanged. Existing
native settings/state refuses a first installation. The settings migration must
exit 0 and candidate `check` must report zero gaps/cascades/globals.

The new root receives `webinfo/rust_config_update_state.json` with format 1,
applied/required schema 1, success status, native package ID/hash and candidate
version. Go's state file is preserved independently. Package defaults only
create missing switch files; they never replace user state.

Preparation is online; after stopping Go a final complete snapshot and new
migration/check preserve shutdown-time data. Binary replacement uses same-dir
atomic rename; the configuration root is renamed as a whole. Each intent and
result is fsynced to a private retained transaction. A detached transient systemd
worker survives SSH disconnection. Ordinary failures restore Go automatically;
an interrupted/killed worker is recovered by the explicit rollback command,
not a permanent boot hook. Both entry points exclude concurrent transaction
workers. Health requires the expected version, service active and three real
DNS answers; native additionally requires runtime Rust and schema 1.

Rollback restores the Go root/program/unit/environment and retains the entire
post-cutover Rust root separately. Later Rust changes are not merged into Go.
Hash failures and unexpected unit/drop-in sets refuse recovery; data and
transaction directories are never automatically removed. Space is budgeted
before staging and again before stopping; refusal does not clean user files.
See [the Chinese operator guide](../cutover.md) and
[F-3b evidence](../validation-records/10-18-f3b/README.md).
